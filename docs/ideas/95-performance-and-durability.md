# 性能与耐久：导线很便宜，日志才是地板

**状态**：候选

**一句话**：纯进程内 Rust 的图，每步固定开销 30–100 ns、吞吐由节点本体决定；日志做成可配置就是耐久旋钮，LSM 让它批量且可查询，但 fsync 那条地板仍在。

**动机**：[94](94-value-proposition.md) 给了四层成本表，但那张表回答的是「能不能跑」，没回答两件事：和 Python 是什么关系，日志写进 LSM 之后地板还在不在。

**形态**：

## 三个天花板

1. **调度**：30–100 ns/步/核。图小、全在 cache 里是 30–60 ns；图大、随机访问吃到 cache miss，100–300 ns。
2. **节点本体**：100 ns–10 µs。取 1 µs 作中位，调度只占 5–10%——这是好消息，瓶颈不在图。
3. **值与分配**：1 KB 的值每步一次搬运 ≈ 100 ns；每次 malloc 20–50 ns，per-run arena 降到 2–5 ns。

多核：值不可变 + 分片就绪队列 + 工作窃取，CPU 密集时接近线性；用 Arc 共享小值会在 4–8 核开始被原子操作拖住，arg 是 benchmark 还是 arena 的取舍。

## 和 Python 比

分三种场景，结论不同：

- **每步是毫秒级工作**（数据库、HTTP、文件）：两者打平，导管成本 <1%，看不出来。score 在这里赢的是结构，不是速度。
- **每步是微秒级逻辑**（几千个小步骤）：score 快 20–100×。对照：Python 一步的 dict/属性/分派管道 1–5 µs，score 的导管 30–100 ns；前提是节点用 Rust 写。
- **节点本身是 Python**（pandas、ML SDK）：速度就是 Python 的，score 只贡献结构。

还有一项常被忽略：启动。Python 解释器 20–50 ms，score 加载一份 plan 约 1 ms 级。CLI 一次性小脚本的体感差距来自这里，不来自执行。

## 压实那一档

纯区压成一个执行单元（[85](85-graph-linearization.md)）：逐元素 1–10 ns，进入查询引擎/数组语言的档位。前提是纯、arena 分配、不跨边界。同一个模型因此有两档速度——图这档（每步几十到几百 ns）与压实这档（每元素几 ns），不要用一个数对外报。

## 日志的三个名字

现在的文档把三样东西都叫 run 文档，于是「要不要每步保存」永远说不清。拆开：

- **checkpoint（状态）**：为了恢复。需要的只有前沿——哪些节点已完成、它们还活着的输出、待读计数、pass 计数。停点保存就够：挂起（等 request）、显式暂停、进程退出前。崩溃丢的是上一个检查点之后的工作；接受这件事的前提是效果幂等（键 = run / step / pass / attempt），或者把检查点卡在效果前后。
- **trace（轨迹）**：为了渲染。内存环形缓冲，可关；关掉时每次事件只多一个分支，磁盘零成本。它不持久，进程死了就没了——这是对的语义，不是缺陷。
- **journal（审计）**：为了从文档完整重放。每步一条、持久、可选；成本就是下面那条 fsync 地板。

三套配置，互不代表：checkpoint（停点 / 每 N 步 / 每个效果前后）、trace（off / on）、journal（off / summary / full）。把它们合成一个「日志开关」，等于把恢复、可视化和审计绑成同一条命。

## journal 的级别

级别是持久化级别，不是文本日志：

- **off**：崩溃丢尾部。纯节点可以（输出可重算），效果节点不行（效果不可重放）。
- **每波批量**：一次提交摊到一波，最划算的一档。
- **每 entry**：fsync 地板，50–500 µs/条。

约束只有一条：能省掉的是 entry，不是效果。纯节点默认 off，效果节点默认记或显式声明幂等；节点级覆盖全局，但覆盖不能把一个不可幂等的效果节点变成 off——那不是配置，那是丢事实。

## LSM 到底买到什么

事实（okm 的 fjall 后端）：`commit_batch` 是一次 `Batch::commit()`，即一条 WAL 写；fjall 默认 Buffer 模式，需要时显式 `persist(PersistMode::SyncData)` 才 fsync（`okm-core/src/engine/fjall_backend.rs:41,88`）。

- **买到**：提交按批摊平（一批一条 WAL 记录）；顺序写、无读-改-写；日志因此可查询（键 = run / pass / step）；与数据同 store 时效果与日志同批（[93](93-score-and-okm.md)）。
- **买不到**：fsync 本身。Buffer 模式下提交约 10–50 µs（耐久窗口 = 刷盘间隔，掉电丢尾部）；SyncData 下约 100–500 µs/提交。后台 compaction 吃 CPU 与 IO，写放大对只写一次的日志是白付的，但可容忍。
- **结论**：LSM 让日志变便宜、可查询、可批，不让它免费。要「不丢」，就把 fsync 按波次做，把地板除以波宽；要「便宜」，就接受一个毫秒级窗口。

**代价**：

- **日志 off 的 run 不能恢复**：节点级覆盖是策略，不是自由；不可幂等的效果节点不能 off。
- **配置面变大**：三样东西各有粒度，默认值必须保守——journal 对效果节点开、trace 关、checkpoint 在停点；否则恢复、可视化、审计会互相拖累。
- **LSM 的读路径多一层**：memtable → L0 → …；热尾部通常在 memtable，冷读才走盘。
- **具体数字依赖盘与文件系统**：NVMe / consumer SSD、ext4 / btrfs，差一倍以上是常态；上表是量级，不是承诺。
