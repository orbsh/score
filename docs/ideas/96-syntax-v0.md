# 语法 v0：连线为主体

**状态**：候选（v0.1，可改）

**一句话**：一段 score 程序是若干「绑定 + 连线」的行；端口写在尖括号里、用竖线分方向（`s<in|out>`），参数写在圆括号里，`->` 顺序接续、`-->` 从头分叉、`-[cond]->` 带条件的分叉。

**动机**：语法要服务三件事——人读起来像流程图、LLM 生成起来像连线、diff 按行。嵌套表达式与位置实参同时破坏这三条。

**形态**：

## 节点与绑定

```
src = read(path: "in.json")
parsed = parse(text: src, schema: Row)
```

- 调用即节点；`名字 = 调用` 建立稳定引用——分支、渲染、diff 都靠它。
- 圆括号只装**具名绑定**（实参），尖括号只装**端口方向**：`s<in|out>(args)`。两者职责不重叠，读的时候不用在同一对括号里找竖线。
- 竖线左边是入口、右边是出口；不关心哪一侧就留空：`s<in|>`、`s<|out>`。两侧都空就是裸 `s`，表示两侧都用默认端口（该侧唯一的那一个，或名为 `in` / `out` 的那一个）。
- 实参一律具名（[89](89-edges.md)）；值只能是字面量或对其它端口的引用。
- `.` 不再是端口语法：它只用于值成员（`record.field`、`Module.Type`）。一个符号一件事。

## 多端口

- 一个绑定是**节点**，端口写在尖括号里：`parsed<|rows>`、`parsed<|errors>`。多输出不需要新语法——一个节点，几个端口。
- **句柄不是值，端口才是值**。节点没有单一的「结果类型」；每个端口各有自己的类型，可以彼此毫不相干（[90](90-types.md)）。所以 `parsed` 单独出现只在「恰好一个输出端口」时才当值用；多输出时它是歧义，validate 拒绝。
- 值位置只能引用出口：`parsed<|rows>`。在值位置写入口（`parsed<rows|>`）是 validate 错误——入口不是值。
- 别名不产生节点：`rows = parsed<|rows>`，渲染上也不画新点。
- 变体端口：`parsed<|ok>` / `parsed<|err>` 是同一个和类型输出的两支，一次只发一个；分支按端口名，不按条件。
- 同一节点的输入与输出可以同名：`step<acc|acc>`。尖括号已经把方向分开了，不需要唯一命名。
- 缺失的输入：调用处给字面量，或端口有声明期默认值；都没有就是 validate 错误（[88](88-containers-and-joins.md)）。

两端都多端口的节点，写法不变——参数在圆括号，方向在尖括号：

```
def split(rows: List<Row>, at: Int) -> (head: List<Row>, tail: List<Row>) {
  head = take(rows: rows, n: at)
  tail = drop(rows: rows, n: at)
}

s = split(rows: src<|rows>, at: 100)
s<|head> -> normalize<rows|>
s<|tail> -> archive<rows|>
```

- 定义：签名把输入端口和输出端口都列出来；输出在体内用同名绑定（这就是 [83](83-subgraph-is-a-function.md) 的「签名 = 端口集合」）。
- 调用：两进两出与一进一出没有语法差别，只有端口名多几个。
- 宿主注册的节点（Rust 函数）同理：签名在算子表里，文本不重述，validate 按表检查。

## 多端口的链：`<in|out>`

```
src -> parse<text|rows>(schema: Row) -> normalize -> store
```

- 尖括号里竖线左边是**入口**、右边是**出口**。读到它不需要查节点定义——方向就写在括号里。
- 空侧用默认端口：`s<|rows>`、`s<text|>`；两侧都空就是裸 `s`。
- 尖括号只属于链上的一步。显式的边写 `x<|a> -> y<b|>`——两端都带方向，不靠位置推断。
- 括号里只能有一对：链一次只搬一个值。要同时用两个输出，写两条边。
- 其余输入照常写在圆括号里：`parse<text|rows>(schema: Row)`。

## 端口方向

- 方向永远写出来：入口在竖线左边，出口在右边。位置不再承担方向，所以读者不必翻签名。
- 一条边：`x<|a> -> y<b|>`——左边是 x 的出口，右边是 y 的入口，两边各写各的。
- 一个值：`x<|a>`。
- 反馈端口 `acc` 在同一轮里既是入口又是出口，正是 `step<acc|acc>` 的形状。
- 定义处仍然靠箭头分界：`def f(a: T) -> (b: U)`。

不采用极性写法（`s<a`、`s>b`、`s<a>b`）：它有两种同义顺序（`s<a>b` 与 `s>b<a`），没有成对定界，而且形状与类型参数 `list<Row>` 相同——三样都是这门语言最不想要的东西：两个写法、一个靠扫描的边界、一个需要靠大小写或上下文猜的歧义。

## 边：一种符号，三种强度

```
src<|rows> -> index<rows|>
```

- 一行一条边；一个输入端口最多一条入边（[89](89-edges.md)），扇出就是同一个出口写多行。
- `->` 顺序接续：值从这里流到那里。
- `-->` 从头分叉：从本链的头另起一支，语义上等价于把前一步再写一遍。
- `-[cond]->` 带条件的分叉：条件臂互相争用同一个 token，恰好一条成立；`-[*]->` 是兜底。
- 长横线读作「多一条路」，方括号读作「一个判断」——两种含义不挤在同一个符号里，`=` 那条箭头形式因此取消。
- **不用 `|>`**：管道暗示「值变成一个函数的输入」，而这里是端口到端口的线；再引入一个同义符号，人和 LLM 都会二选一，格式化器与 diff 也会分裂。

## 链：`->` 接续，`-->` 回头部

```
parsed = parse(src)
  -> normalize
  -> validate
  -> store
  --> report
```

- 一行以 `->` 开头：接续上一条路径——接在上一行最后一个节点后面。**换行只是排版**：下面这段和把它们连成一行完全等价，一行里放几个 `->` 也随意。

```
s -> a
->b
->c ->d ->e
->f
```

- 一行以 `-->` 开头：从**本链的头**（这一组的第一行）另起一支；之后的行继续跟着这一支走（当前路径变成那一支的末尾）。
- 空行与注释不结束一组；缩进无意义。只有出现新的头（不以箭头开头的行）才开新的一组。
- 所以顺序程序可以一行一步往下写，几百步也一样；分支不靠缩进，靠 `-->`。
- 要从链中间分叉：把那个节点绑出来，再以它开头写新的一组。`-->` 永远回到头，这是它唯一的语义，因此可预测：

```
  -> v = validate
v -> enrich --> archive
```

`v -> enrich` 接在 v 后面；`--> archive` 回到这一组的头（v），所以 archive 是 v 的另一支，不是 enrich 的下游。

- 链只是糖：规范形式是「一行一条边」，格式化器可以在两种写法之间展开与折叠，语义只有图。
- **引用不是声明**：单独一行写 `v` 只是把已有节点重新指定为这一组的头，不新建节点。长文件里要就近分叉，就在使用处把名字再写一遍——这是「拉近」的正规做法，不是格式化器的特权。

## 条件：`-[expr]->`，只在行首

```
parsed<|rows> -[rows.len == 0]-> skip
parsed<|rows> -[*]-> bulk
```

- 条件必然是一个分支：同一个源端口的条件臂互相争用同一个 token，恰好一条成立。所以条件没有「接续」的写法——写成 `->` 是不存在的。
- 标签里的裸名字先查**源节点的端口**，再查常量；要引用别的节点就写全 `x<|p>`。所以 `-[rows.len == 0]->` 不用把 `parsed` 再写一遍。
- `[*]` 是兜底，互斥分支必须有它（[89](89-edges.md)）。
- 单条条件臂、没有 `[*]`，就是守卫：目标可能不跑。validate 要检查目标路径能容忍缺席（目标的每个输入都来自守卫边，或目标是汇），否则就是死等。
- 条件分叉和 `-->` 一样从**头**出发，所以中段的条件分支要先绑名再起一组；分支点因此总有名字。
- 表达式的作用域只有上述端口与常量（[82](82-graph-is-the-semantics.md)）；没有副作用、没有用户函数、没有循环。

## 子图

```
def normalize(text: Text) -> (rows: List<Row>) {
  @doc "Trim, parse, validate"
  @tags [etl]
  @budget 100

  t = trim(text)
  rows = parse(t)          # 与输出端口同名 = 绑定该端口
}
```

- 签名就是端口；输入参数在体内可直接引用，输出端口用同名绑定。
- `@` 开头是元信息：渲染、文档、默认预算。除 `@budget` 外都不参与语义。
- 调用子图与调用节点同形：`n = normalize(text: src)`。子图因此是「程序内定义的一种节点」，调用语法只有一种。

## 容器

```
p = map(normalize) over src<|rows>
t = fold(sum, init: 0) over p
```

- 前缀形式：先看跑几次，再看体内。元素绑定到子图的第一个输入端口，其余参数具名给出。
- `map(...)` 与 `fold(...)` 是关键字产生式，不是节点引用，不参与端口语法。
- 预算可以写在实例上：`map(normalize, budget: 1000) over xs`。

## 常量

```
const timeout = 30
```

可被 run 创建时的覆盖替换（[91](91-constants-and-config.md)）。

## 环（未定）

v0.1 不定义环的语法。环需要两个只有它才有的东西——反馈端口的 seed、环上的 budget——这两个目前都没有位置：`-[]->` 已经被条件占用，不能再兼作属性标签。等环的语法定下来时一并给它们位置，不先借一个宽泛的边缘标签口。

## 两个完整例子

ETL：

```
src = read(path: "in.json")
parsed = parse(text: src, schema: Row)
parsed<|rows>
  -> normalize
  -> v = validate

v<|bad> -[bad.len == 0]-> store
v<|bad> -[bad.len > 0]-> report
```

`validate` 的输出绑成 `v`，两条条件臂从 `v<|bad>` 分叉——分支点是名字，不是位置。

游戏规则（宿主注册节点，外部接口封闭）：

```
u = unit(id: e<|unit>)
d = damage(u: u, amount: e<|amount>)
d<|unit> -[unit.hp_percent < 30]-> sound(name: "low_hp")
```

这是一条守卫：没有 `[*]`，`sound` 是汇，不响就是没发生。

## 为什么是这一版

- 三种括号各一件事：`( )` 只装参数，`< >` 只装端口方向，`[ ]` 只装条件，`{ }` 只装子图体。
- 方向不用查签名：括号里就写着入口和出口。
- 多端口的链不断：`<in|out>` 把一进一出写在同一处。
- 箭头的长短就是语义：`->` 一条路，`-->` 两条路，`-[cond]->` 按条件选一条。
- 一行一条边：diff 干净；LLM 只需生成「名字 + 箭头」，不需要算拓扑序。
- 名字是唯一的分支引用：不存在「第几个」这种位置引用。
- 子图与节点同形：调用只有一种写法，validate 只多一步「展开」。

**代价**：

- 一个引用最多挂两对括号：`parse<text|rows>(schema: Row)`。
- 空的半边（`<|rows>`）看起来像漏写，格式化器得把它对齐。
- 尖括号与类型参数 `list<Row>` 同形，靠位置区分（类型在声明里，端口在引用里）。
- 谓词里的裸名字依赖「先查源端口」的作用域规则，读者要记得。
- 五种写法要记：`->`、`-->`、`-[...]->`、`<in|out>`、裸 `s`。
- `-->` 回到头，长文件里分叉点与源头离得远，要靠命名或格式化器拉近。
- 守卫边让「目标可能不跑」成为合法状态，validate 多一条路径检查，否则死等会伪装成 waiting。
- 环没有语法，环上的 seed 与 budget 也没有位置。
