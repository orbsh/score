# 类型：标量、数组、记录与和

**状态**：在用（可改）

**一句话**：端口上的类型是一个闭合的小代数——bool / int / float / text / bytes、list<T>、map<text,T>、record{...}、带标签的和；记录按结构相等，和按变体名相等；名字只是别名。

**动机**：

- 端口要能说「这个人的 name 与 age」，否则 validate 只能检查「是个 object」，typed port 就退化成注释。
- 记录给静态检查与渲染一个单位；但再往上（继承、trait、方法）方向就反了：方法属于节点（操作），不属于值。
- 结构化身份让二进制图与图库导出不需要注册表：类型表可以规范化，名字不承载语义。

**形态**：

- **标量**：bool、int、float、text、bytes。没有 null；缺席是 option<T>。数值分 int 与 float，JSON 只有一个 number，跨边界时按端口类型解码。
- **容器**：list<T>、map<text, T>。JSON 的键只有文本，别的键类型写成 list<record{key, value}>——这是格式的限制，不是隐藏能力。
- **记录**：record{字段: T, ...}，默认闭合。加一个字段是破坏性变化。
- **和（带标签）**：`A{...} | B{...}`，变体名是身份（名义），载荷是类型；编码用外部标签（`{"A": …}` / `{"type":"A", …}`）。和值可以带着标签流动，也可以在产生点用变体端口拆开（[89](89-edges.md)）。
- **option / result 是特例**：`option<T>` = `None | Some<T>`，`result<T,E>` = `Ok<T> | Err<E>`。
- **别名**：`type Person = record{...}` 只是别名；同结构即同类型，同名不同结构是错误。和类型没有别名带来的等价性——变体名就是身份。
- **检查**：端口按结构相等比对，不做子类型；需要「宽记录当窄的用」就在节点里显式投影。
- **编码**：类型是二进制图的一节（[87](87-binary-graph-is-the-artifact.md)），值仍是 JSON（[41](41-json-boundary.md)）。

## 布局与偏移

进程内的值不是通用 JSON，而是按类型铺开的槽位：

- **record**：字段按规范序排成槽位数组，字段 i 在 `slots[i]`。规范序是硬要求——两个实现排出不同的序，偏移就对不上。
- **和**：tag 占第一槽，载荷一槽；tag 是变体序号，不是字符串。
- **list<T>**：向量。**map<text,T>**：哈希表——这是唯一必须哈希的地方，键是数据不是 schema；想按偏移访问就写成 record。
- **标量**：int / float / bool 内联；text / bytes 是引用（Rc/Arc 或 arena 偏移）。

名字转偏移发生在两处：谓词与实参里的字段引用在类型检查时解成下标；和上的字段访问先分裂（类型系统强制），之后一次 tag 检查加偏移。运行期没有字段名查找。

解码只在边界做一次（parse 节点），之后内部值都带布局；线格式仍是 JSON，跨进程再序列化回去。代价：边界一遍解码、两套表示要维持一致、schema 变化让带布局的产物失效、map 仍然哈希。

**代价**：

- **二进制格式多一张类型表**：图库导出要带上它；导出即用，但仍要过 validate。
- **记录闭合**：演进要靠别名或显式的开放记录（开放记录本身还没定）。
- **大数组按值传递**：值不可变，更新是复制；容器里的大数组要注意预算（[88](88-containers-and-joins.md)）与内存（[56](56-hierarchical-arena.md)）。
- **两条身份规则**：记录结构相等、和名义相等；教的时候要分开说，编码器也要分开规范化。
- **和值带标签**：跨边界时必须按标签解码，不能当裸记录；类型表要带变体名与载荷。
- **穷尽性进 validate**：每个变体被接线或显式忽略，否则拒绝——这是和类型最值钱的那部分，且不依赖类型推导。
- **规范化是硬要求**：结构相等意味着字段顺序不影响身份；两个编码器各排一份，就会得到两份「同类型」，不同实现之间的类型表要能对齐。
