# 容器与 combine：实例化的两个参数

**状态**：在用（可改）

**一句话**：一个子图实例只定两件事——体内怎么跑（一次性、逐元素、归约）与等到几个 token（zip、merge、collect，即 combine）；两件都改就绪规则，所以都进内核，不做成库函数。

**动机**：

- 就绪规则不能被库函数改。普通节点是「输入齐了就跑」，zip 要两边都到，merge 任一边到就跑，collect 要够 n 个；调度器不认这些规则就不知道该等谁。
- 缺席要变成值。option 上下文让「上游没跑」也是一个 token（空值），消费者不必逐点判空；这比给端口加一个运行期的「可选」标志干净——那个第三状态一旦存在，readiness 就要分支。
- 不开放成通用 monad：bind 的顺序语义（State、IO）并行调度器兑现不了。上下文固定三种。
- 不叫 monad/functor：模式是「怎么用」的属性，不是「是什么」的属性；同一张子图这里被 map、那里被 zip。子图只声明能力。

**形态**：

实例 = （子图，上下文，模式，预算 max）。上下文固定三种：list / option / result。

模式三种：

- **一次性**：内联（[83](83-subgraph-is-a-function.md)），整张图摊进调用点。
- **逐元素**：map / flatmap / filter。逐元素跑体内子图，结果按元素序收集；flatmap 拼接，顺序 = 元素序 × 内部序；filter 是 flatmap 的 0 或 1，不独立成一种语义。元素独立，可并行。
- **归约（fold）**：body 比逐元素多一对端口——累加器入、累加器出，内核线程化，list 跑完发一次结果。顺序，不并行；默认每次迭代一条 entry，声明 body 为纯则可压成一条边界记录（[85](85-graph-linearization.md)）。累加器住内核的循环变量，不住图上的单元。

fold 的两义必须分开：对 list 的 fold 是归约模式；对时间的 fold（跨 pass 累积、步数只由预算界定）是环（[89](89-edges.md)）。区分的是数据源，不是算子。

上下文：

- **list**：元素独立，可并行。
- **option**：0 或 1 次，缺席自动穿过容器链——容器套容器时不必逐层判空。
- **result**：元素独立，失败作为值继续走。

combine 是节点种类，不是库函数：

- **zip**：每个输入都有 token 才发一次，配成对。只到一边的 token 要排队，必须有上限或声明 last-wins。
- **merge**：任一到就发一次，不配对。schematic 今天「两条边进同一个点得到两趟」就是它。
- **collect(n)**：攒够 n 个发一次，输出一条 list；可能等很久，图上显示为 waiting 而不是 stuck。

seed：环的反馈端口在第 0 轮用一次声明的初值。它不是默认值（默认值分不清「还没到」和「这一轮没有」），也不是第二条边（一个输入端口只有一条边；再插一个合并就又要 combine，而 combine 自己也要 seed）。语义等价于 FRP 的 iPre。validate 查：每个环至少一个 seeded 端口，或一个只发一次的入口；环内至少一条边有 budget。

必需/可选删除：端口要么接线（引用），要么写字面量（默认）；运行期缺席必须是一个值。schematic 的「Optional inputs」因此关闭。

不拿 FRP 的：连续时间算子（integral、derivative、debounce）、switch（动态拓扑，静态审计与定价随之失效）、sample（读别人的最近值＝隐式依赖）。fold 见上：list 上是归约，时间上是环。

子图属性：名字、文档、预算、默认模式——都是元数据。不带「图可见的可变状态」，理由按严重程度排：

- **重放会坏**：写序由调度决定，两个分支同写一个单元，日志里的先后是运行期的偶然；要么每次写一条 entry（日志从「每节点一条」变成「每写一条」），要么放弃从文档重放。
- **并行会死**：不可变是分支自动并行的前提；共享单元要么加锁、要么定序，两条都要求调度器重新理解数据依赖。
- **分布式会贵**：单元要有一个「家」，每次访问是 RPC；不可变值跨机器只是字节（[73](73-not-general-purpose.md)）。
- **效率被高估**：跨节点省的是拷贝，而一次节点完成通常是毫秒级调用，拷几 KB 是噪声；真正需要就地更新的大数组累加与遍历属于节点内部——宿主语言里随便 mutate，图看不见。

允许的中间形态只有一种：纯子图内部可以可变——写不出边界、每次调用重置、对外仍是纯函数，等于函数体内的局部变量；压实/编译时它天然成立（[85](85-graph-linearization.md)），日志仍只记边界那一条。

真要跨节点的状态，那是外部存储节点：get / put 是效果，读写的时刻与值进日志，按数据库对待，不是语言原语。

**代价**：

- 运行文档变成矩阵：键要能表达（容器，元素，内层步骤，pass）；容器挂起时要保存哪些元素完成、哪些在等。
- 失败策略三选一（整体失败 / 元素 Result / 跳过），必须写进容器语义。
- 元素间默认串行还是并行要定：串行让 map 失去一半价值，并行要求体内无状态。
- 预算 max 是硬要求，否则宽度由数据决定，不可定价。
- 容器内挂起（内层 request 等人）会让一个实例同时有多种状态，渲染与调试都要按元素显示。
- **归约只能顺序**：并行归约要求 body 可结合（结合律要声明），v1 不做；一条大 list 的 fold 因此是延迟的主要来源。
