# 流与批：入口声明类型，不引入流原语

**状态**：在用（可改）

**一句话**：没有「流」这个概念，也没有「批」这个概念——只有 list 类型；入口端口的类型决定这一次 run 拿到的是一个值还是一条 list；要持续地来，就是重复的 run，或者另一种运行形态。

**动机**：FRP 的另一半（连续时间、采样、窗口）很吸引人，但流会同时打破三条：完成、定价、审计。先问这三条能不能让，再谈要不要流。

**形态**：

- **list 是类型构造子，不是调度原语**（[90](90-types.md)）。它可以嵌套（`list<list<T>>`），可以出现在任何端口上；调度只看 token，一个 token 就是一条 list。
- **入口的端口类型就是声明**：`list<T>` 表示这一次 run 处理一条 list，`T` 表示一个值。数学上单值是长度 1 的 list，但模型里两者都是「一个 token」——不存在特例分支。
- **增量性靠重复**：一次 run 一条 list；要连续处理，就是多次 run（或 service 形态）。容器（[88](88-containers-and-joins.md)）逐元素跑，逐元素的开销留在 run 内。
- **真流是另一种运行形态**：长驻、有背压、按时间窗/关闭信号完成、日志按批或摘要、budget 变成速率。它叫 service run，与 plan run 并列，不是 plan run 的扩展。

**代价**：

- **没有细粒度增量**：一条 list 里改一个元素要整条重算，除非容器内部有增量算法——那是节点的实现细节，不是模型给的。
- **批的粒度就是延迟的粒度**：谁划分批，谁定延迟。
- **真流要两套语义**：第二套完成判定、第二套审计粒度、第二个运行时。
- **budget 的计量单位要选**：按 token 还是按元素；按元素就把 list 的成本前移到预算检查里。

**冲突**：[88](88-containers-and-joins.md)（容器按元素跑，combine 决定配对）、[85](85-graph-linearization.md)（完成 = 无 token 可动）、[89](89-edges.md)（token 是单位）、[90](90-types.md)（list 是类型）、[73](73-not-general-purpose.md)（协调语言：细粒度循环属于节点，不属于图）。

**若改掉会动到**：入口与源节点的声明、scheduler 的完成判定、budget 的计量单位、审计粒度、渲染（list 的展开与折叠）。
