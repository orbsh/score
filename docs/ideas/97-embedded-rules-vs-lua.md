# 嵌入式规则：与 Lua 比

**状态**：候选

**一句话**：score 适合「事件 → 条件 → 动作」的规则图，赢在沙箱、可审计、可重放、可渲染；Lua 赢在任意逻辑、逐帧过程代码与二十年的嵌入经验。逐帧的玩法代码不该用 score 写。

**动机**：游戏规则是「外部接口封闭」的嵌入式脚本场景——宿主注册一组节点，脚本只能调它们。这正好是 score 的形状；但把它和 Lua 混为一谈，会得出错误的期望。

**形态**：

## 分工

- **规则图**（score）：什么时候、在什么条件下、按什么顺序做哪几件事。事件源是宿主节点，动作也是宿主节点。
- **玩法代码**（Rust 或 Lua）：一次动作内部的计算——寻路、伤害公式、AI 状态机。这些留在节点里。
- 判据：能用「当 X 且 Y 时做 Z」说清的，写成图；需要写算法的，写成节点。

## 逐项对比

| 维度 | score | Lua |
| --- | --- | --- |
| 沙箱 | 只能调注册的节点，没有 `os`、没有任意代码 | 受限环境，历史上逃逸案例多 |
| 可审计 | 每步一条 entry，可回放 | 要自己搭 |
| 可重放 | run 文档即重放 | 要自己搭（确定性、随机源、输入捕获） |
| 可视化 | 图即程序 | 文本 |
| 热重载 | 换定义，run 继续 | 换函数，闭包与已捕获状态要自己处理 |
| 表达力 | 谓词表达式加节点；写不了算法 | 通用 |
| 逐帧性能 | 每节点 30–100 ns 加节点工作（[95](95-performance-and-durability.md)），逐帧逐实体要小心 | LuaJIT 快，且有二十年优化 |
| 生态 | 无 | 大 |

## 结论

- **规则、事件、触发器**：score 更好，尤其是有 mod 的场景——不可信代码只能碰注册节点，这个边界比 Lua 沙箱可靠得多。
- **逐帧玩法**：Lua（或直接 Rust）更好；score 在这个位置会把每个实体的每次更新都变成一次调度。
- **混合**：宿主用 Rust，玩法用 Rust，规则用 score，规则通过节点调用玩法。三者的边界就是节点表。

## 表达式语言：这个场景把它请回来

游戏规则把谓词推到前台：`hp < 30 && enemy.near && !cooldown`。只用节点拼这些条件会爆炸。所以这个场景是「叶子表达式请回来」的最强论据。

但要限定：无副作用、只读本节点端口与常量、无用户函数、无循环；它是一台几十条指令的小求值器（[82](82-graph-is-the-semantics.md)、[90](90-types.md)）。它不是把表达式语言请回来当主体，而是给 `-[...]->` 一个够用的语言。

**代价**：

- **规则多时图会碎**：几十条规则就是几十张小图，要按事件分组、折叠；渲染的 LOD 是必需品，不是装饰。
- **「哪些规则生效」是配置不是图**：模式、难度、开关放在 run 创建时的覆盖里（[91](91-constants-and-config.md)），别塞进图。
- **逐帧的预算与日志策略要重定**：60Hz 下每步一条 entry 不可行，只能采样或关掉（[95](95-performance-and-durability.md)）。
- **没有生态**：节点库要自己长；这决定了第一版能做什么（[73](73-not-general-purpose.md)）。
