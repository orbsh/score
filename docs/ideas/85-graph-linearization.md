# 图的线性化：顺序、跳转与可挂起帧

**状态**：在用（可改）

**一句话**：图是偏序，顺序代码是全序的延拓；编译就是选一个延拓、把剩下的选择点显式化，唯一的例外是等待——它要求目标机有可恢复帧。

**动机**：图的收益之一是能在任何满足偏序的次序上执行，代价是执行前必须先选一个次序。把这件事说清楚，才知道「图能编译到顺序+跳转」成立到什么程度：成立，但目标不是普通栈机。

**形态**：

目标形式不限定：自建字节码、wasm 模块或其它都可以；图这一层只规定怎么把偏序压成顺序，不规定产物的字节格式（[77](77-bytecode-vm.md) 是候选载体）。

三种落法，按宿主能力选：

- **静态拓扑序 + 分支跳转**：每步一个基本块，控制边走跳转；分支是一次 switch 或跳转表。
- **工作表解释**：图当字节码——每步一个小函数、一张就绪计数表、一个分派循环。结构是编译出来的，叶子是解释的。
- **状态机/续延**：每步返回下一个 frontier，挂起就是返回续延；run 文档扮演续延本身。

一条例外：request 是真挂起，「顺序+跳转」里没有这条指令。目标机要么有可挂起帧，要么把整份 run 文档当续延在外层重入。所以准确说法是「顺序 + 跳转 + 可挂起帧」。

反向也成立：一份 plan 编成叶子的顺序程序——每步一个函数、跨步状态在一个 struct、分支编成 match、等待编成显式返回——再整体编成字节码或 wasm。图仍然为真值，产物是叶子语言；运行时不需要调度器。

**代价**：

- **选次序会丢掉并发**：偏序里有并行分支时，顺序目标必须插入调度（fork/join 或工作队列），那是运行时不是编译器。
- **层级在产物里消失**：产物只剩线性代码，分层显示与「点进子图」要靠调试信息找回边界。
- **什么时候值得生成代码要实测**：几十到几百步时，「编译结构 + 解释叶子」通常比生成代码划算；阈值来自测量，不来自推断。
