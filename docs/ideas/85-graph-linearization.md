# 图的线性化：顺序、跳转与可挂起帧

**状态**：在用（可改）

**一句话**：图是偏序，顺序代码是全序的延拓；编译就是选一个延拓、把剩下的选择点显式化，唯一的例外是等待——它要求目标机有可恢复帧。

**动机**：图的收益之一是能在任何满足偏序的次序上执行，代价是执行前必须先选一个次序。把这件事说清楚，才知道「图能编译到顺序+跳转」成立到什么程度：成立，但目标不是普通栈机。

**形态**：

目标形式不限定：自建字节码、wasm 模块或其它都可以；图这一层只规定怎么把偏序压成顺序，不规定产物的字节格式（[77](77-bytecode-vm.md) 是候选载体）。

三种落法，按宿主能力选：

- **静态拓扑序 + 分支跳转**：每步一个基本块，控制边走跳转；分支是一次 switch 或跳转表。
- **工作表解释**：图当字节码——每步一个小函数、一张就绪计数表、一个分派循环。结构是编译出来的，叶子是解释的。
- **状态机/续延**：每步返回下一个 frontier，挂起就是返回续延；run 文档扮演续延本身。

一条例外：request 是真挂起，「顺序+跳转」里没有这条指令。目标机要么有可挂起帧，要么把整份 run 文档当续延在外层重入。所以准确说法是「顺序 + 跳转 + 可挂起帧」。

反向也成立：一份 plan 编成叶子的顺序程序——每步一个函数、跨步状态在一个 struct、分支编成 match、等待编成显式返回——再整体编成字节码或 wasm。图仍然为真值，产物是叶子语言；运行时不需要调度器。

## 为什么不是栈机

五处差别，都不是实现细节：

1. **状态不是栈，是端口邮箱**。栈机的状态是操作数栈加局部变量；这里的机器状态是「每个输入端口这一轮有没有 token、值是什么」，本质是一张映射表，没有 push / pop。
2. **控制不是 pc，是就绪集**。「下一条指令」不是 pc+1，而是任一个就绪的节点；执行是工作列表选择，不是线性取指。
3. **挂起不是栈快照，是日志**。栈机挂起要把栈整个存下来；这里挂起就是把 run 文档落盘、恢复就是读回来重算 marking。这条才是它能等一个人几天、能换机器恢复的原因，而 [83](83-subgraph-is-a-function.md) 已经写明它没有调用栈。
4. **指令集大半是外部调用**。机器自己只做：发 token、等、按端口路由（[89](89-edges.md)）、按变体匹配、combine、seed、budget。算术在节点里，不在指令里。
5. **地址空间不是单一的**。节点可以在不同宿主上跑，跨机器的值是字节；栈机默认一台机器一个地址空间。

换个类比：位置 = 端口，变迁 = 节点，token = 值——它更接近 Petri 网或数据流机。真要「编译」，产物是一张调度表或一段工作列表程序，不是 push / load / add。

两个 VM 别混：这里是**调度器**（数据流机），谓词那边是**求值器**（常规的小表达式 VM，或直接树遍历）。后者几十条指令，栈式或寄存器式都行，不影响架构；先树遍历，测出来再说。

测量判据：只有当 profile 显示 fold（就绪集、计数器、路径解析）占 run 时间的显著份额——上万个小节点、全是进程内函数、没有挂起——才把无环部分编成直线调用或做纯节点融合。只要节点经常跨进程、等外部回答，fold 就是噪声，编译不解决问题。

## 压实与寻址

压实（把一段图编成一个执行单元）只有一个合法范围：子图。[84](84-folding-fidelity.md) 已经保证子图的边界就是端口，压它切不到边；压任意连通区会切断中间那条边，「接口就是端口」随之不成立。

三条约束：

1. **接口是端口**：内部名字对外消失；同一定义的多个实例共享一份产物，缓存键 = 定义 hash + 引擎版本。
2. **只压纯区**：无外部调用、无挂起、无时钟与随机。含外部调用的区，收益被分派吃掉。
3. **日志是分水岭**：保留内部日志，编译只去调度开销，语义不变（可暂停、可审计、可部分恢复）；压成一条边界记录，快，但内部不可审计、不可在中间挂起——后者必须是子图的显式声明（不透明区），不能是优化器的默认动作。

省的是就绪检查、路由与日志，乘内部节点数；算术在节点里，一分不省。外部调用占大头时，这个乘数再大也被淹没。

寻址分两层：

- **端口名**：产物里必须是名字（人读、图库存、diff 都靠它），运行期不必。加载时驻留一次，之后每步是下标——这一步与编译无关，编译只是把驻留提前，不多赚。量级上：一次哈希几十纳秒，一次下标一纳秒级；三个端口一万次执行差不到一毫秒，对比毫秒级的外部调用看不见。它只在「一串纯节点」里才有意义，而那正是压实场景，且加载时驻留已经解决。
- **值内部的字段**：这才是大头。通用 JSON map 每读一个字段一次哈希；边界 parse 成类型化表示（[90](90-types.md) 的 record 有已知布局）之后，字段访问是偏移。这是 Parse, Don't Validate 的第二层收益，靠的是端口两侧类型一致，执行器可以在边界解码成带布局的记录。

顺序因此是：先把值类型化（边界解码），再谈压实；端口驻留随时做；编译图放最后，且只压纯区。压实是缓存，不是编译期分析，不引入不动点（[57](57-linear-compile.md)）。

**代价**：

- **选次序会丢掉并发**：偏序里有并行分支时，顺序目标必须插入调度（fork/join 或工作队列），那是运行时不是编译器。
- **层级在产物里消失**：产物只剩线性代码，分层显示与「点进子图」要靠调试信息找回边界。
- **什么时候值得生成代码要实测**：几十到几百步时，「编译结构 + 解释叶子」通常比生成代码划算；阈值来自测量，不来自推断。
- **压实的失效与调试**：产物跟着定义 hash 与引擎版本走，改定义就要重编；调试要一张「节点 → 代码偏移」的映射，映射本身是格式的一部分。
